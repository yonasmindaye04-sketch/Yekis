Document Purpose & Scope
This document is the authoritative technical playbook for the Development & Engineering department building the Ethiopian Freelance Marketplace. It consolidates all engineering requirements, compliance obligations, architectural decisions, and implementation timelines into a single, actionable reference.
This playbook is designed to answer four questions:
WHAT to build: Features, architecture, data models, and integrations required.
HOW to build it compliantly: KYC/AML, PDPP data protection, security, and audit requirements embedded in every technical decision.
WHEN to build it: Phased roadmap with sprint allocations, dependencies, and hard gates.
WHAT remains open: Regulatory questions, partner dependencies, and technical risks to monitor.

Cross-reference: For legal strategy, contract templates, and regulatory analysis, see the Master Design, Legal & Compliance Document (Draft 1). This playbook assumes familiarity with that document but is self-contained for day-to-day engineering work.

2.2 Database Setup
Primary Database (PostgreSQL 15+): ACID-compliant relational database for all transactional data
Audit Extension (pgaudit): Logs every SELECT, INSERT, UPDATE, DELETE with user identity and timestamp
Immutable Storage (Immudb Vault (or PostgreSQL WORM partition)): Tamper-evident storage for KYC, transaction, and dispute records — 10-year retention
Encryption at Rest (AES-256): Database-level encryption for all tables; row-level encryption for TIN, bank accounts, ID numbers
Encryption in Transit (TLS 1.3): All API and database connections
Backup Strategy (Daily encrypted backups to Ethiopian cloud + weekly encrypted backups to DR site with SCCs): RPO: 1 hour; RTO: 4 hours
2.3 Repository & CI/CD
Initialize Git repository (GitHub/GitLab) with GitFlow branching model (main, develop, feature/*, hotfix/*)
Set up automated CI/CD pipelines: build → unit tests → integration tests → security scan → deploy to staging → deploy to production
Secret management: Use HashiCorp Vault or AWS Secrets Manager (Ethiopian-hosted instance). No secrets in code or .env files committed to repo.
Environment separation: development (local), staging (pre-prod), production (live). Each with isolated database and API credentials.
Infrastructure as Code (IaC): Terraform or CloudFormation for reproducible Ethiopian cloud infrastructure deployment.

3. Core Platform Foundation
3.1 User Authentication & Security
Session Management: JWT (JSON Web Tokens) with short expiry (15-min access token, 7-day refresh token)
Transport Security: TLS 1.3 enforced on all endpoints; HSTS headers; secure cookie flags (HttpOnly, Secure, SameSite=Strict)
Two-Factor Authentication: OTP via SMS (Twilio/Infobip Ethiopian route) or TOTP authenticator app for sensitive actions (withdrawals, profile changes)
Password Storage: bcrypt with cost factor 12+; minimum password complexity enforced
Rate Limiting: 100 requests/minute per IP for auth endpoints; 10 failed login attempts trigger a 15-minute lockout + email alert
Device Fingerprinting: Track device ID + IP geolocation; flag logins from new devices or foreign IPs for review

Legal Marking: All freelancer profiles must display a clear 'Independent Contractor' status badge. This is a legal requirement to prevent misclassification under Labour Proclamation No. 1156/2019.
3.3 Job Engine
Job Posting: Clients create standardized job posts using templates that enforce independent-contractor terms.
Proposal Submission: Freelancers browse/filter jobs and submit proposals with price, timeline, and portfolio links.
Contract Generation: On bid acceptance, the system auto-generates a PDF/digital Master Service Agreement (MSA) from the contract template. The MSA is stored in the user's project history and linked to the escrow record.
Milestone Definition: Each contract includes 1–3 milestones with defined deliverables, payment tranches, and review periods.
Status Tracking: Real-time project status visible to both parties: Draft → Funded → In Progress → Under Review → Completed / Disputed.
3.4 Security from Day 1
Encryption Everywhere: TLS 1.3 for all traffic; AES-256 at rest for all databases and file stores
Access Controls: RBAC (Role-Based Access Control) on every endpoint; principle of least privilege
Audit Trails: Every action (login, profile change, payment, dispute action) logged with user ID, timestamp, IP, and action type
Input Validation: Strict validation on all API inputs; parameterized queries to prevent SQL injection; CSP headers to prevent XSS
API Rate Limiting: Tiered rate limits: 100 req/min for authenticated users, 20 req/min for anonymous, 5 req/min for auth endpoints
Dependency Scanning: Automated vulnerability scanning (Snyk/Dependabot) in CI/CD pipeline; block deployment on critical findings

4. KYC & Compliance Layer
4.1 Fayda ID Integration (Primary KYC Method)
Ethiopia's national digital ID system (Fayda ID, Proclamation No. 1284/2023) provides biometric-linked, government-verified identity. The National Bank of Ethiopia (NBE) mandates that all financial accounts be Fayda-linked by 2026. Integration with VeriFayda 2 API is the strongest defense against ghost accounts.

Data Minimization: Store only the hashed national ID number, verification timestamp, and KYC status. Raw biometric data (photos, fingerprints) must NOT be retained on platform servers — only the verification result from Fayda.

5.3 Automated Cron Jobs
Auto-Release Escrow (Every hour): Check all 'Under Review' milestones where review period (5 days) has expired → auto-release funds to freelancer
Payment Reminder (Daily at 9 AM): Send reminder to clients with pending milestone reviews 24h before auto-release

TMS Red Flag Scan (Every 15 minutes): Run automated TMS rules across last 24h of transactions; flag anomalies for Compliance Officer review

VAT Note: The platform's commission revenue is subject to 15% VAT once annual revenue exceeds ETB 1,000,000. VAT is NOT deducted from freelancer payouts — it is the platform's tax obligation on its own revenue. The system must track platform revenue separately and generate VAT reports quarterly.
5.5 Idempotency and Reliability
Idempotent Payment EndpointsAll payment-related API endpoints must be idempotent (same request ID = same result). Use idempotency keys for all escrow operations to prevent double-charging or double-payout.
Webhook VerificationVerify every payment webhook signature before processing. Re-query payment provider API for status confirmation if webhook is delayed or missing.
Dead Letter QueueFailed payment operations (webhook failures, API timeouts) must be queued for retry with exponential backoff (max 5 retries, then manual review).
Reconciliation JobDaily automated reconciliation: sum of all escrow balances must equal sum of all client deposits minus released funds minus platform fees. Any mismatch triggers immediate alert.
Circuit Breaker PatternIf a payment provider API is down, circuit breaker opens; queue new payments; notify users; retry every 5 minutes. Prevent cascading failures.

6. In-App Evidence & Dispute Flow
6.1 Real-Time Messaging
All project communication must occur within the platform's messaging system. Off-platform communication (WhatsApp, Telegram DMs) is explicitly excluded from dispute evidence. This is stated in the Terms of Service and reinforced with UI warnings.
Encryption: All messages encrypted at rest (AES-256) and in transit (TLS 1.3)
Immutability: Messages cannot be edited or deleted by users once sent. Admins can append moderator notes but cannot alter original content.
File Attachments: Max 50MB per file; scanned for malware; stored in encrypted file store with retention tied to project lifecycle
Read Receipts: Timestamped delivery and read confirmations stored as evidence metadata
Export Capability: Full message thread exportable as PDF/JSON for dispute evidence bundles
6.2 Milestone Submission UI
Freelancer uploads files or provides links for each milestone deliverable.
System auto-generates a submission record with: timestamp, file hash (SHA-256), uploader identity, and linked milestone ID.
Client receives notification with preview capability (for images, PDFs, videos) and download links.
All submissions are versioned — if freelancer submits revised work, previous versions are retained for audit.
6.3 Dispute Resolution Dashboard (Admin View)
The dispute dashboard is the primary tool for platform mediators. It must present all evidence in a structured, non-editable format with clear audit trails.

6.4 Audit Trails for Disputes
Admin Action Logging: Every mediator action (status change, message to user, evidence review) logged with: admin ID, timestamp, action type, before/after state
Immutable Storage: Admin logs stored in WORM-compliant storage (Immudb Vault). No delete or edit permissions for any role, including super-admin.
Chain of Custody: Evidence bundles must include: hash of each file, timestamp of compilation, mediator identity, and digital signature
Retention: All dispute records retained for 10 years per AML Proclamation, regardless of dispute outcome

7. Security Audits & Pilot Launch
7.1 Penetration Testing
Scope: External perimeter (web app, APIs, mobile), internal infrastructure (database, file store), and social engineering (phishing simulation)
Focus Areas: Escrow logic bypass attempts, KYC hard-block circumvention, payment webhook manipulation, privilege escalation, SQL injection, XSS
Provider: Engage an Ethiopian-registered or internationally certified security firm (e.g., CREST-accredited)
Timeline: 2–3 weeks for initial test; 1 week for remediation validation
Deliverables: Executive summary, detailed vulnerability report with CVSS scores, remediation roadmap, re-test confirmation
7.2 Encryption & Hardening Checklist
TLS Configuration: TLS 1.3 only; disable TLS 1.0/1.1; strong cipher suites (ECDHE-RSA-AES256-GCM-SHA384); HSTS max-age=31536000
Server Hardening: Disable unused ports/services; fail2ban for SSH; automated OS patching; minimal container images (Distroless/Alpine)
Database Hardening: No direct internet exposure; connection via VPC/private network; parameterized queries only; regular vulnerability scans
API Security: Rate limiting, input validation, CORS restrictions, API key rotation, OAuth 2.0 for third-party integrations
Frontend Security: Content Security Policy (CSP), XSS protection headers, CSRF tokens, secure cookie attributes
7.3 Closed Beta Protocol
Cohort Size: 50 freelancers in ONE category (recommended: Graphic Design — high demand, clear deliverables, easy to evaluate)
Client Recruitment: 10–15 local SMEs/startups with real design needs; offer discounted platform fees (5% instead of 10%) for beta participation
Test Funds: Use Chapa sandbox mode for all payments during beta. No real money moves until security audit passes.
Success Criteria: 100% of escrow-funded projects complete without manual intervention; <5% dispute rate; <2% payment failure rate; KYC pass rate >80%
Feedback Collection: In-app feedback widget; weekly check-in calls with 10% of beta users; structured exit survey
7.4 User Flow Analytics
Signup Flow: Track: landing page → registration start → email verification → KYC initiation → KYC completion. Target: >60% completion rate.
Job Posting Flow: Track: client login → create job → define milestones → fund escrow. Target: >70% fund-after-post rate.
Proposal Flow: Track: freelancer login → browse jobs → submit proposal → bid accepted. Target: >15% proposal-to-accept rate.
Payment Flow: Track: milestone delivery → client review → acceptance → fund release. Target: >90% on-time release rate.
Drop-off Alerts: Automated alerts when drop-off rate at any step exceeds 20% in a 7-day window
7.5 Feedback Loop & Iteration
Daily standup during beta: review yesterday's bug reports, plan today's fixes.
Weekly sprint retrospective: what worked, what didn't, what to change before public launch.
Bi-weekly stakeholder demo: show progress to leadership, legal, and compliance teams.
Go/No-Go Decision Gate: After 4 weeks of beta, evaluate against success criteria. If 3+ criteria met → schedule public launch. If <3 met → extend beta by 2 weeks.

8. Testing, Security, and Launch Verification
8.1 Automated Testing
8.1.1 Unit Tests
Escrow State Machine: Test ALL valid transitions: Payment Pending → Escrow Held → Under Review → Released/Disputed/Refunded. Test invalid transitions (e.g., cannot move from 'Released' back to 'Escrow Held'). Target: 100% state coverage.
KYC Hard-Block Logic: Test that unverified users are blocked from: bidding, accepting jobs, depositing, withdrawing, receiving payments. Test edge cases: user verified mid-transaction, user suspended after deposit.
Tax Calculation Engine: Test withholding tax at 3% (with TIN) and 30% (without TIN). Test VAT calculation on platform commission. Test rounding behavior and edge cases (ETB 0.01 precision).
Payment Idempotency: Test that duplicate payment requests with same idempotency key return identical results without double-charging.
Cron Job Logic: Test auto-release trigger at exactly 5 days + 0 hours. Test timezone handling (EAT, UTC+3).
8.1.2 Integration Tests
Mock Payment Flows: Mock Chapa, Telebirr, and CBE APIs to simulate: successful payment, failed payment, delayed webhook, duplicate webhook, timeout.
Fayda ID Verification: Mock Fayda API responses: valid ID, invalid ID, expired OTP, biometric mismatch, API downtime.
Dispute Evidence Compilation: Test automatic evidence bundle generation: contract PDF, message thread, milestone submissions, payment records. Verify bundle hash integrity.
Data Rights Tools: Test 'Download My Data' export: verify all user data included, format compliance (JSON/CSV), 30-day SLA. Test 'Delete Account' flow: verify non-AML data purged, AML data retained with logical delete flag.
8.2 Manual End-to-End Testing
Happy Path: Client posts job → Freelancer bids → Client accepts → Client funds escrow (Chapa/Telebirr) → Freelancer delivers → Client accepts → Funds release → Both parties rate each other.
Dispute Path: Client posts job → Freelancer bids → Client accepts → Client funds escrow → Freelancer delivers → Client rejects → Dispute opened → Evidence submitted → Mediator recommends → Client accepts recommendation → Partial release.
Auto-Release Path: Client posts job → Freelancer bids → Client accepts → Client funds escrow → Freelancer delivers → Client silent for 5 days → Auto-release triggered → Funds released → Client can still rate.
KYC Block Path: Unverified freelancer tries to bid → Blocked with clear message → Freelancer completes KYC → Bid succeeds.
Suspicious Activity Path: New user deposits ETB 600,000 in 3 transactions within 6 hours → TMS flags structuring → Compliance Officer notified → Account suspended → STR filed within 24h.
8.3 Security Compliance Verification
10-Year Retention: Verify WORM storage is operational: attempt to delete a 1-year-old transaction record → must fail. Attempt to modify an audit log entry → must fail.
Data Erasure Rules: Submit test 'Delete Account' request → verify non-AML data (marketing prefs, chat history) is purged within 30 days. Verify AML data (KYC docs, transactions) is retained with anonymization.
Encryption Verification: Run SSL Labs scan on production domain → must score A+. Run database encryption verification → confirm AES-256 at rest.
Access Control Audit: Attempt to access admin endpoints with client credentials → must return 403. Attempt to access another user's escrow data → must return 403.
Backup Recovery Test: Quarterly: restore from backup to isolated environment → verify data integrity → confirm RTO (4 hours) and RPO (1 hour) met.

11. Escrow & Payment Integration — Open Questions for Regulators & Partners
The following questions must be resolved with regulators and payment partners before finalizing the escrow architecture. These are technical dependencies that block engineering decisions.
11.1 NBE Licensing Clarification
Does the chosen escrow model (in-wallet, bank custodian, or third-party PSP) require a Payment System Operator or Payment Instrument Issuer license?
If the platform holds client funds internally (even briefly), does NBE classify it as a payment gateway?
Are there any exemptions for escrow-only services that do not offer wallet storage beyond the project duration?
What is the minimum capital requirement for each license type (quoted as ETB 3M+ for payment gateway operators)?
Does NBE offer a sandbox or regulatory guidance program for fintech startups?
11.2 Telebirr Onboarding Questions
What is the exact process to register as a Telebirr merchant/agent for the platform?
What API integration requirements, fees, and settlement times apply?
Confirm daily and per-transaction limits (NBE directive: 75k ETB/tx, 150k ETB/day).
Does Telebirr support split disbursements (e.g., simultaneous payout to freelancer and platform commission deduction)?
What is the dispute/reversal process for incorrect Telebirr payments?
Is there a public sandbox environment, or must all testing be done against production with test accounts?
11.3 CBE Integration Questions
Does CBE provide a direct API for CBE Birr merchant integration, or is reference-based verification the only path?
How can merchants automatically verify CBE fund transfers (FT reference system)?
What fees apply to corporate escrow accounts?
Does CBE support instant interbank transfers via EthSwitch for freelancer payouts?
What is the timeline and documentation required for a corporate merchant account?
11.4 Chapa Details
Can Chapa act purely as a passthrough (non-custodial) if desired, or does it always hold funds temporarily?
What fees and settlement schedule apply specifically to a marketplace model (vs. standard merchant)?
Does Chapa support split disbursements (instantaneous payouts to freelancers net of platform fee)?
What is the refund/dispute process for Chapa-processed payments?
Can Chapa provide webhook reliability SLAs (delivery guarantee, retry policy)?
Does Chapa's KYC process satisfy NBE requirements, or must the platform run parallel KYC?
11.5 KYC/AML Compliance Questions
What transaction thresholds trigger enhanced KYC for an online marketplace (vs. a bank)?
How does the platform register with the Financial Intelligence Center (FIC) for STR filing?
What specific record-keeping formats does FIC require (10-year retention per Proclamation No. 1387/2025)?
Can the platform rely on Chapa's KYC for payment users, or must it maintain independent KYC records?
What are the penalties for delayed or missed STR filing?
11.6 Data / Telecom Regulations
Does routing payments via telecom networks (Telebirr, M-PESA) require additional telecom licenses or ECA security standards?
What are the data localization requirements for payment transaction logs (beyond PDPP Art. 22)?
Are there specific encryption standards mandated by ECA for telecom-integrated fintech platforms?
11.7 Arbitration Logistics
Contact AACCSA to confirm: current name, arbitration rules, fee schedule, and typical timeline.
How to formally include AACCSA rules in platform contracts (incorporation by reference vs. explicit terms)?
Does AACCSA offer online/virtual arbitration hearings?
What evidence format does AACCSA accept (digital bundles, PDFs, authenticated chat exports)?
11.8 Tax and Float Questions
If the platform holds funds in escrow (even briefly), does this create a VAT or interest tax obligation?
Can the platform earn interest on escrow float, or is this prohibited by NBE or Ethiopian banking law?
How does Safaricom's M-PESA entry into Ethiopia affect Telebirr usage limits and competitive dynamics?
What are the exact ERCA reporting requirements for a platform acting as a withholding agent?

12. Development Roadmap (Phases 0–5)
This roadmap breaks the project into 6 phases with concrete tasks, timelines, and compliance checkpoints. At each phase, technical work is aligned with Ethiopia's legal requirements (PDPP, AML/KYC, tax law) and fintech best practices.
12.1 Phase 0: System Architecture & Infrastructure (Sprint 1)
Duration: 2 weeks | Sprint: Sprint 1 | Blocking Risk: ALL downstream engineering blocked until infrastructure is provisioned
Data Localization & Hosting: Provision local servers in Ethiopia (Ethio Telecom Cloud or Safaricom Ethiopia). Verify PDPP Art. 22 compliance: all personal data stored domestically. Configure full encryption at rest (AES-256) and in transit (TLS 1.3).
Database Setup: Deploy PostgreSQL 15+ with pgaudit extension for detailed activity logging. Configure WORM storage or immutable ledger (Immudb Vault) for 10+ year retention of audit logs and financial records.
Repository & CI/CD: Initialize Git repository (GitHub/GitLab) with GitFlow branching model. Set up automated pipelines for build, test, and deploy to staging and production. Implement secret management (HashiCorp Vault or AWS Secrets Manager).
Sandbox API Keys: Register for sandbox credentials: Fayda ID (national eKYC), Chapa (payment aggregator), Telebirr (mobile money), CBE Birr (bank wallet). Document all API credentials in secrets manager — never in code.
12.2 Phase 1: Core Platform Foundation (Sprints 2–3)
Duration: 4 weeks | Sprints: 2–3 | Blocking Risk: No user-facing features until auth and profiles are functional
User Authentication: Build secure login/registration: JWT sessions, TLS enforcement, 2FA (OTP via SMS or authenticator app). Password storage: bcrypt with cost factor 12+. Implement device fingerprinting and geolocation checks.
User Profiles & Roles: Create Freelancer and Client profiles with portfolio uploads. Mark profiles as 'Independent Contractor' for legal clarity. Implement role-based access control (RBAC) on all endpoints.
Job Engine: Develop job posting and bidding UIs. Clients create standardized job posts (templates enforce independent-contractor terms). Freelancers browse, filter, and submit proposals. Auto-generate PDF/digital Service Agreement on bid acceptance.
Security from Day 1: Integrate encryption (TLS everywhere), access controls on every endpoint, audit trails for all actions. Biometric or PIN login for mobile. Follow fintech best practices.
12.3 Phase 2: KYC & Compliance Layer (Sprints 4–5)
Duration: 4 weeks | Sprints: 4–5 | Blocking Risk: NO financial transactions allowed until KYC is operational
Fayda ID Integration: Link user onboarding to Ethiopia's Fayda digital ID system. Call VeriFayda 2 API for OTP, facial recognition, and fingerprint matching. Align with NBE mandate: all financial accounts Fayda-linked by 2026. Store only hashed ID number and verification timestamp.
Hard-Block Logic: Enforce: unverified users CANNOT deposit, withdraw, or accept jobs. Mark unverified accounts in database. Disable escrow actions until verification succeeds. Build user-facing KYC status dashboard.
Data Retention & Erasure: Implement account-deletion feature: purge personal/profile data on request, except financial/KYC logs retained 10 years for AML. Use logical delete flag to segregate 'deleted' profiles while preserving transactions and audit trails. Explain in UI that full deletion is not immediate due to legal retention.
Transaction Monitoring System (TMS): Build automated red-flag detection: structuring, velocity spikes, round amounts, rapid movement, PEP activity. Integrate PEP/sanctions screening with daily list refreshes.
12.4 Phase 3: Escrow & Payment Engine (Sprints 6–7)
Duration: 4 weeks | Sprints: 6–7 | Blocking Risk: Platform cannot generate revenue without working payments
Payment Gateway Integration: Implement APIs for Telebirr (Ethio Telecom mobile money) and CBE Birr (Commercial Bank of Ethiopia wallet). User flow: client chooses method → backend sends payment request → user confirms on device → webhook notifies backend of success/failure. For Chapa: integrate aggregator API for card/bank payments. Use merchant sandbox accounts for development.
Escrow State Machine: Code escrow logic: Payment Pending → Escrow Held (all funds secured) → Partially/Fully Released or Refunded. Handle multi-milestone jobs by releasing partial payments on each milestone approval.
Automated Cron Jobs: Auto-release escrow if client is silent for defined period after milestone delivery. Send reminders before timeouts. Run every hour; handle timezone (EAT, UTC+3).
Platform Accounting: On each transaction, compute: platform fee (10%), withholding tax (3% with TIN, 30% without), VAT (15% on commission). Freelancer share: 90% minus withholding. Platform revenue: 10% plus 15% VAT on commission.
Tax Reporting: Log all payment events with details for tax filings (gross amount, tax withheld, VAT). Ensure accounting can produce CSV/statement for ERCA on demand.
Idempotency and Reliability: All payment endpoints idempotent (same request ID = same result). Verify each payment status with provider rather than assuming webhook success. Re-query Telebirr transaction if webhook is delayed. Implement dead letter queue for failed operations.
12.5 Phase 4: In-App Evidence & Dispute Flow (Sprints 8–9)
Duration: 4 weeks | Sprints: 8–9 | Blocking Risk: Disputes cannot be resolved without evidence infrastructure
Real-Time Messaging: Build in-app chat between client and freelancer per project. Log all messages and file attachments (encrypted at rest). Include UI warnings: off-platform communications (WhatsApp) won't count in disputes.
Milestone Submission UI: Enable freelancers to submit files/links for each milestone. Tag submissions in chat/project record. Auto-generate submission record: timestamp, file hash (SHA-256), uploader identity, milestone ID.
Dispute Resolution Dashboard: Create admin view for disputes: Stage 1 (Direct Negotiation — monitor only), Stage 2 (Mediation — admin intervention). Compile evidence bundle: chat logs, contracts, deliverables. Maintain versioned records.
Audit Trails: Ensure every admin action (status change, message to user) is logged immutably (pgaudit + WORM). Audit trail supports fair resolution and compliance.
12.6 Phase 5: Security Audits & Pilot Launch (Sprints 10–11)
Duration: 4 weeks | Sprints: 10–11 | Blocking Risk: Public launch blocked until security audit passes
Penetration Testing: Engage external security firm to test escrow logic, KYC bypass attempts, payment webhook manipulation, privilege escalation. Scope: external perimeter, internal infrastructure, social engineering.
Encryption & Hardening: Verify TLS 1.3 everywhere, AES-256 at rest, strong ciphers, disabled unused ports/services, automated patching. Review server configurations and security headers.
Closed Beta: Invite 50 freelancers in ONE category (Graphic Design recommended) and 10–15 local SMEs. Use Chapa sandbox for all payments. Success criteria: 100% escrow completion without manual intervention, <5% dispute rate, <2% payment failure.
Monitor User Flows: Instrument analytics on key flows: signup → KYC → job post → escrow fund → delivery → release. Watch for drop-offs (e.g., Fayda verification abandonment).
Feedback Loop: Collect bug reports and feedback. Schedule quick iterations (UX tweaks, bug fixes) before full launch. Go/No-Go decision after 4 weeks: 3+ criteria met → public launch; <3 met → extend beta 2 weeks.

Appendix D: Glossary of Terms
AACCSA: Addis Ababa Chamber of Commerce and Sectoral Associations — arbitral institution for commercial disputes.
AML: Anti-Money Laundering — laws and procedures to prevent money laundering and terrorist financing.
CDD: Customer Due Diligence — the process of verifying the identity of customers to assess risk.
DPIA: Data Protection Impact Assessment — mandatory assessment under PDPP for high-risk processing activities.
DPO: Data Protection Officer — mandatory role under PDPP for large-scale or sensitive data processing.
ECA: Ethiopian Communications Authority — regulator for data protection and telecom under PDPP.
ERCA: Ethiopian Revenue and Customs Authority — tax collection agency.
Fayda ID: Ethiopia's national digital ID system (Proclamation No. 1284/2023) — biometric-linked, government-verified identity.
FIC: Financial Intelligence Center — receives and analyzes Suspicious Transaction Reports (STRs).
HSM: Hardware Security Module — physical device for secure key management.
KYC: Know Your Customer — identity verification process required by AML regulations.
NBE: National Bank of Ethiopia — central bank regulating payment systems and AML.
PDPP: Personal Data Protection Proclamation No. 1321/2024 — Ethiopia's GDPR-like data protection law.
PEP: Politically Exposed Person — individual with prominent public function, requiring enhanced due diligence.
PSP: Payment Service Provider — licensed entity authorized to provide payment services.
ROPA: Register of Processing Activities — mandatory documentation of all data processing under PDPP Art. 30.
SCCs: Standard Contractual Clauses — ECA-approved contractual safeguards for cross-border data transfers.
STR: Suspicious Transaction Report — mandatory filing to FIC within 24 hours of detecting suspicious activity.
TIN: Tax Identification Number — required for 3% withholding tax rate (30% without TIN).
TMS: Transaction Monitoring System — automated system for detecting AML red flags.
WORM: Write Once Read Many — immutable storage that prevents deletion or modification of records.
VAT: Value Added Tax — 15% on platform commission revenue once annual revenue exceeds ETB 1,000,000.
