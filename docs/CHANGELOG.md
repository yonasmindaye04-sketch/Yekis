  - **Sign-in refused a phone number.** The API has always accepted one — `identifier`, `email` and `phone` are all read, and `normalizeLoginIdentifier` turns `0911223344`, `251911223344` and `+251911223344` into the same `+251…` before the lookup — but the **sign-in field was `type="email"`**, so the browser's own validation refused the number ("Please include an '@' in the email address") and the request never left the page. The field now takes either and sends the value as `identifier`; the label says so in every language, built from the two labels the interface already had rather than a new string.
  - **An address could not create an account.** The Mini App's sign-up took a number only, and derived a synthetic `@yekis.local` address from it. An address is accepted now, and it is **proven with the same six-digit code** the web sign-up uses (`OnboardingVerification` is channel-generic) before the account exists — an unproven address is somebody else's inbox, and it is the login identifier.
  - **The account gets the reserved placeholder number.** `User.phone` is non-null and unique because it is the payout destination, so it cannot simply be left empty; an account created from an address alone is given the `+2510…` block no operator is allocated, which is what the federated sign-ins (Google, Apple, Facebook, Telegram all hand out no number) have always used. Writing a made-up `+2519…` would put somebody else's real subscriber number into the PII store and could collide with a live subscriber, breaking that person's login. The consequence is honest: such an account can use the platform and is identified by its address, but it cannot receive a payout until a number is claimed for it — a KYC step, not a sign-up one.
  - **Backend** (`apps/backend/src/modules/auth/auth.service.ts`, `apps/backend/src/schemas.ts`, `packages/schemas/src/index.ts`): `RegisterInput.phone` is optional and accepts the placeholder shape; `registerUser` creates the account through `withPlaceholderPhone`, so a placeholder collision is retried rather than surfacing as a unique-constraint error. The duplicate check and the phone-proof adoption both apply only when a number was given.
  - **Frontend** (`apps/frontend/src/App.tsx`, `FullPlatformApp.tsx`, `api/client.ts`): the Mini App's code step takes over the panel while the address is being proven, with the tab switcher hidden and the component's own "use a different email" link back to the form; `api.login` sends `identifier` rather than `email`.

- **An onboarding OTP over email, and a signup flow that can be completed on a hosted test deployment (2026-11-13)** — the signup flow proved control of the phone number over SMS and nothing else, so on the deployed testing instance the very first onboarding step failed for every new user and the account could not be created at all. The frontend made it look like it worked: the API's `503` was swallowed by the offline mock's HTTP-status fallback, which answered with a fabricated `devCode` (482910) that the server had never issued, and the code could then never be verified. The onboarding now uses **email**, and the step itself was rebuilt around one question: what does the person need to do next?
  - **Backend** (`apps/backend/src/modules/auth/email-verification.service.ts`, `email-verification.routes.ts`). `POST /api/v1/auth/email/code` and `POST /api/v1/auth/email/verify` are unauthenticated because the code is proven *before* the account exists; neither reveals whether an address is registered, and "no such code" and "wrong code" answer identically. The code is stored only as a salted SHA-256, expires in 10 minutes, is capped at 5 attempts, is throttled per address, and a resend invalidates the previous code. A failed delivery deletes the challenge rather than reporting success for a message nobody received.
  - **Channel discovery** — `GET /api/v1/auth/verification/channels` returns which channels can actually deliver on this host, derived from the SMTP and SMS configuration and nothing else. The client asks before it offers, because a host with no SMS key cannot send a text and offering one anyway is how a signup dead-ends with no explanation. It is allowlisted as a public route in `tests/fixtures/publicRoutes.ts` and listed in `tests/fixtures/unauthenticatedByDesign.ts`.
  - **Registration adopts the proof** — `registerUser` now reads a recent email proof and stamps `User.emailVerified` and `User.emailVerifiedAt` on the new row, exactly as it already did for the phone number. `User.email` is the login identifier and the destination of every transactional mail, so an unproven address is somebody else's inbox. `User.emailVerified` already existed and is also set by the OAuth path, where the provider — not the platform — proved the address; `emailVerifiedAt` records only what this platform proved by email OTP.
  - **Schema** — migration `20261113120000_email_verification_otp` adds the `EmailVerificationCode` table and the `User.emailVerifiedAt` column. Only the salted hash of the code is stored, and verified rows are kept as the audit trail of which address was ever proven.
  - **Frontend** (`apps/frontend/src/OnboardingVerification.tsx`, replacing `PhoneVerification.tsx`). A two-step onboarding: step 1 is the details form with a line saying what happens next; step 2 takes over the panel with the code already requested, the target masked (`a***@example.com`, `+251 *** 344`), the expiry counting down, resend on its own cooldown, and wrong code / expired / too many attempts / undeliverable mail as four different messages. "Use a different email" returns to step 1 with the address still filled in. The escape hatch stays — a hard gate with no way through is a support queue, not a security control.
  - **The `503` is no longer masked** (`apps/frontend/src/api/client.ts`) — the OTP endpoints opt out of the offline mock's HTTP-status fallback, so a server that cannot deliver a code says so instead of answering with a code it never issued. The network-failure fallback is untouched, so the frontend still runs with no backend at all.
  - **Discovery is a hint, not a gate** (`apps/frontend/src/FullPlatformApp.tsx`) — if `GET /api/v1/auth/verification/channels` cannot be answered, the signup falls back to email rather than to "no channel". Falling back to "no channel" would register an unproven address silently; falling back to email sends the user to the step that reports the real delivery error. A `429` now carries the server's own error code, so "too many codes requested for this address" is distinguishable from "too many incorrect guesses" — both are a `429`, and they are very different things to be told.
  - **Outside production**, a host with no SMTP credentials writes the code to the server log instead of failing, so a testing deployment can complete the flow. In production a missing SMTP configuration is a misconfiguration and the caller is told the message was not delivered. The password-reset mail path is untouched: a reset token is a live bearer credential and is never printed outside development.
  - **The SMS phone codes are deliberately left alone.** `User.phone` is the Telebirr / M-Pesa payout destination and the withdrawal-approval code is money. That flow is not weakened to make signup work.
  - **Coverage** — `apps/backend/tests/email-verification.test.ts` (24 tests) covers the negative properties: the code is never recoverable from the database, a wrong code is bounded and counted, an expired code is refused, a resend invalidates the previous code, the endpoint never says whether an address is registered, registration adopts the proof and leaves an unproven address alone, and the production path refuses to report success for a message that was not sent.

- **A container that runs the whole platform, and a deployment runbook for AletCloud (2026-11-12)** - the repository now builds one image that serves the API, serves the built SPA and runs a `redis-server` on loopback, and `docs/ALETCLOUD_DEPLOYMENT.md` describes how to deploy it to a sovereign Ethiopian cloud for testing.
  - **`Dockerfile` (repository root)** - a multi-stage build: pnpm workspace install, Prisma client generation, the API compile and the Vite build, then a runtime stage with the compiled output, the Prisma CLI and its engines, and `redis-server`. A root `Dockerfile` is also what stops a hosting platform's stack detection from picking the wrong thing: it reads the root `package.json`, sees `vite` and `react-dom`, and would offer to build a static site with `npm run build` — which fails anyway, because the workspace is pnpm and there is no `package-lock.json`. The runtime stage copies with `--chown=node:node` rather than chowning afterwards: a recursive `chown` over the pnpm node_modules tree took over seven minutes in the first build of this image, in an extra layer that duplicated the metadata of the two gigabytes below it.
  - **`infra/docker/entrypoint.sh`** - starts the bundled Redis (unless `REDIS_URL` names another host), applies `prisma migrate deploy` before the API starts (a platform does not do this, and a database missing the schema behind a healthy port is a deployment that looks alive and is not), then runs the API as a child process and forwards termination signals to it so a rolling release stops the old container gracefully.
  - **The API now serves the SPA (`apps/backend/src/lib/staticSite.ts`)** - the Telegram Mini App opens the platform in a webview that refuses a page from a different origin, so the SPA and the API have to share an origin, and therefore a port and a TLS certificate. The API's strict JSON-only security headers (`default-src 'none'`, `X-Frame-Options: DENY`) are now scoped to the API routes: applied to an HTML document they would block the page's own script and style tags and refuse to let the Telegram webview frame the app at all. The SPA gets its own headers, including the `frame-ancestors` allowlist that browsers ignore in a `<meta>` policy and therefore has to travel as a response header. `scripts/check-doc-parity.mjs` now fails CI when the two copies of that allowlist drift apart, and the check was verified by breaking one of them and watching the gate fail.
  - **The object store accepts the standard AWS names** - `AWS_ENDPOINT_URL`, `AWS_REGION`, `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY` and `AWS_BUCKET` are now aliases for the `OBJECT_STORE_*` variables, which is what a hosted platform injects when a bucket is linked to an app. The explicit names always win. The region and the addressing style (path-style, which MinIO requires, versus virtual-host style) are configurable rather than hardcoded, because the endpoint is not always AWS and the region is often not `us-east-1`.
  - **The production CSP can name the object store's origin** (`VITE_OBJECT_STORE_ORIGIN`, build-time). The staff console renders a KYC document as an `<img src>` whose URL is a presigned object-store URL, so the browser fetches it from the store's own origin — and the Content-Security-Policy has to name that origin in its `img-src` or the browser blocks it. Without this the document preview was a broken image and the compliance reviewer could not review the document at all. The value is a deployment-specific origin rather than a hardcoded provider hostname, so widening it for one deployment does not widen it for any other.
  - **New configuration**: `SERVE_FRONTEND`, `FRONTEND_DIST_DIR`, `OBJECT_STORE_REGION`, `OBJECT_STORE_FORCE_PATH_STYLE`, `HSTS_INCLUDE_SUBDOMAINS`, `RUN_MIGRATIONS`.
  - **A `container` job in CI** - the deployment image is built and the entrypoint is checked on every push. Nothing else in CI exercises that path, so a break in the Dockerfile would otherwise only surface at deploy time, on the platform, under time pressure.
  - **`scripts/check-deployment.mjs`** - checks a deployed instance against the contract it has to meet: the health endpoint, the API's strict JSON-only policy, the SPA served as HTML, the `frame-ancestors` allowlist arriving as a response header, the absence of `X-Frame-Options` on the SPA, a client-side route reaching the SPA, an unknown API route still answering with JSON, and the two sharing an origin. - **Service levels are enforced server-side (2026-11-12)** (`apps/backend/src/modules/sla/sla.service.ts`, new module; `chat.service.ts`, `dispute.service.ts`, `admin.routes.ts`). The Roadmap's helpdesk SLAs — "general support within 24 hours" and "disputes within 3 business days" — were previously a number drawn in the browser: the ops console computed "hours since the ticket was created" and coloured it. Nothing was enforced, nothing was stored, and nothing could be reported on.
  - **Two clocks per queue.** Support: first staff reply (24 h) and the ticket being closed (72 h). Disputes: the mediator answering (3 business days) and the dispute reaching `RESOLVED` (7 business days). The dispute first-response clock deliberately does not start at the raise: Stage 1 negotiation is designed to run seven days, so that reading would be breached by construction.
  - **Only the facts are stored** — `Conversation.firstRespondedAt`, `Conversation.resolvedAt`, `Dispute.firstRespondedAt` (migration `20261112140000_sla_tracking`). The deadlines are **derived** from `createdAt` plus the configured targets, so changing a target applies immediately to every open item and there is no stored deadline to go stale.
  - **Written once.** A later reply cannot rewrite the first response, and a late reply does not un-breach a clock that was already missed: a breach is a fact about what happened, not a snapshot of the present.
  - **Business days are Monday to Saturday**; Sunday is the only excluded day. Public holidays are not excluded — there is no holiday calendar in the system, and inventing one would silently drift from reality.
  - The state rides on `GET /api/v1/chat/admin/conversations` and `GET /api/v1/disputes/staff/queue`; `GET /api/v1/admin/sla/summary` counts the open queues by breach state. The ops console renders the server's state instead of recomputing it, and both queues can filter to breached cases.
  - **Not escalated.** A breach is visible, countable and filterable; nothing is automatically reassigned, escalated to a supervisor, or auto-closed. Enforcement that moves work between people without a human deciding is a larger decision than an MVP should make quietly.
  - Covered by `apps/backend/tests/sla-enforcement.test.ts`.

### Fixed
- **A mixed-case email address produced an account that could not sign in** — the onboarding step proves the address and then creates the account with the address exactly as the form held it, but every other path that touches `User.email` already uses the lower-cased form: the login lookup lower-cases it, the OAuth path lower-cases it, and the email OTP proof is issued and looked up against it. An account registered as `Alice@Example.com` was therefore created, stamped `emailVerified: true`, and then refused its own password at the sign-in that immediately followed — and because the account existed by then, every retry hit the duplicate path and failed identically, so the address was locked out permanently. `registerUser` now stores the canonical (lower-cased, trimmed) form and matches the duplicate check case-insensitively, so the same mailbox cannot end up with two accounts spelled differently either. The same canonical form fixed a silent no-op in the authenticated branch of `verifyEmailCode`, which stamped `emailVerified` with an exact-match filter against a column that may hold a differently-cased value — the endpoint answered `verified: true` while updating nothing. Three regression tests cover both.
- **The public Privacy Policy and Terms of Service were placeholder documents** — both pages still carried `[TODO: Date]`, a handful of short generic sections, and no operational content; the Terms also promised a five-day release window although the implemented window is seven days, while the old privacy Markdown claimed two- and five-year retention periods that contradicted the ten-year financial and audit rules in the code. The two pages now use the shared editorial layout and the complete section set described above, with the corrected seven-day release and cooling-off periods, the current 7%/0% fee model, consent-aware analytics, the data-subject export/erasure flow, and the retained AML and financial categories. `docs/privacy-policy.md` is no longer a 29-line summary, and `docs/terms-of-service.md` now exists as the published counterpart to the in-app Terms.
- **Behind a proxy, every visitor shared one rate-limit bucket** - `TRUST_PROXY_HOPS` was unset on the deployment, so Express ignored the `X-Forwarded-For` header the platform's edge sends and took the proxy's address as the client's. Every user then shared a single rate-limit bucket: the limit applied to the whole platform rather than to each user, and one busy client could lock everybody else out. express-rate-limit says so in the logs, once per request ("The 'X-Forwarded-For' header is set but the Express 'trust proxy' setting is false"). The deployment now sets it to `1` — the number of hops the edge actually adds — and the warning stops. The runbook explains why one hop and not more: too high and a client could forge addresses to choose its own bucket.
- **The container image generated a Prisma client for the wrong OpenSSL target** - Prisma's detection of the installed OpenSSL failed inside the container build ("Prisma failed to detect the libssl/openssl version... Defaulting to openssl-1.1.x"), so the client was generated for `debian-openssl-1.1.x` while the Debian 12 image needs `debian-openssl-3.0.x`. The result was an image that started, served its port, served the SPA, and then failed **every** database query with "Prisma Client could not locate the Query Engine for runtime debian-openssl-3.0.x" — while the container itself looked perfectly healthy, because the platform's check is a TCP connection. The generator block now names `binaryTargets = ["native", "debian-openssl-3.0.x"]`, which makes the build deterministic instead of dependent on what the detection manages to find.
- **A CRLF line ending would have stopped the deployment container from starting** - the repository is developed on Windows (`core.autocrlf=true`), so every text file is checked out with CRLF endings. A shell script with CRLF endings has a shebang reading `#!/bin/sh\r`, which the kernel cannot resolve, and its line continuations break. This is not theoretical: the first image built from this Dockerfile failed to start with `exec /usr/local/bin/yekis-entrypoint: no such file or directory` — an error that points at the image rather than at the file, and that says nothing about line endings. Nothing in the repository could have caught it: there was no `.gitattributes`, and the only shell script in the project was a PowerShell one. `.gitattributes` now keeps `*.sh`, the `Dockerfile` and the `.dockerignore` LF in the repository *and* in a Windows checkout, and the `Dockerfile` strips any stray `\r` from the entrypoint as it copies it in, so the image is correct even when the source arrived another way (a zip upload, a patch applied by hand).
- **Every staging deployment ran with outbound TLS certificate verification disabled** - `server.ts` set `NODE_TLS_REJECT_UNAUTHORIZED=0` whenever `NODE_ENV !== "production"`. That is a process-wide switch: it turned off certificate checking for *every* outbound HTTPS call the process made — the object store, the Telegram API, every provider callback — and it did so on exactly the environments most likely to be publicly reachable. It is now permitted in two cases only: a development build, and a deployment explicitly pointed at the Telebirr **sandbox** gateway, whose certificate really is self-signed (`TELEBIRR_ENV` is already mandatory whenever any Telebirr credential is set, so "sandbox" is a statement of intent rather than a default). A staging deployment now verifies certificates, and a production one always did. The decision is a pure function, `tlsVerificationBypassed()` in `config/env.ts`, so it can be asserted directly instead of by killing a test runner.
- **The withdrawal-approval endpoint answered 500 when the SMS gateway was down** — `POST /api/v1/escrow/wallet/withdraw/otp` mapped only its own error types, so the SMS provider's failures fell through to the generic handler. The caller was told the platform had broken when the gateway had not, and a retry looked like a server fault rather than a transient one. It now answers **503 `SMS_UNAVAILABLE`** when a code cannot be delivered and **429 `RATE_LIMITED`** when the number is being spammed, mirroring the phone-verification route. Covered by a new regression test in `tests/withdrawal-2fa.test.ts`.
- **The browser-platform sidebar scrolled away with the body content** — `.platform-shell.sh-shell` is a grid, so the sidebar was a grid item and the grid stretched it to the height of the main content. On a long page it became taller than the viewport and scrolled off with the body, taking the navigation with it: by the bottom of the page there was no way to change section. The base rule now sets `position: sticky`, `align-self: start`, `height: 100vh` and `overflow-y: auto`, so the sidebar is pinned to the viewport and scrolls its own contents if the nav is taller than the screen. The `sh-variant-inset` and `sh-variant-floating` variants already declared a `top` and a viewport-relative `height` — those were inert without `position: sticky` and now do what they were written to do. The topbar was already frozen, and the ops-console sidebar was already `position: fixed`; the browser platform was the only one that scrolled.
  - **Verified, not assumed.** `scripts/verify-sidebar-fixed.mjs` drives headless Chrome over the DevTools Protocol (Node's built-in WebSocket — no browser-automation dependency) and measures the sidebar's viewport-relative position before and after scrolling the page. With the old CSS the sidebar's top went from `10` to `-1224` — entirely out of view. With the fix it stays at `10` and every check passes.
