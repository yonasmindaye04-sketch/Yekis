### Removed
- **Chatwoot third-party agent inbox (2026-10-03)**: the Chatwoot integration built earlier the same day has been fully reverted. It was working (Application API client, signature-verified webhook, two-way message and status sync — all verified end to end against a live v4.18.0), but it was the wrong shape for this product:
  - It required a **public HTTPS tunnel** for webhooks. Chatwoot runs deliveries through `ssrf_filter`, which rejects every private/loopback address with no flag to relax it, so agent replies were silently undeliverable in local development and would have needed a public ingress in production.
  - It added a **second inbox, a second message store and a second UI** alongside the staff dashboard that already had a working support queue.
  - Its launcher bubble is **third-party and unstyleable**, which is precisely the "not embedded the way we want it" problem it was meant to solve.
  - It cost a ~3 GB container stack (its own Postgres and Redis) for capabilities the platform already had: realtime messaging, typing, read receipts, attachments, ticket assignment/claim/reassign, OPEN/CLOSED workflow, unread queues and audit trail.

  Everything the native path was missing turned out to be **scoped guest access** (see the Added entry above), not an agent inbox. Removed: the widget component and its SDK bridge, the Application API client, the bridge service, the webhook receiver, the signature helpers, `docker-compose.chatwoot.yml`, `.env.chatwoot.example`, the `chatwoot:*` npm scripts, all `CHATWOOT_*` env vars and both `.env` entries, and the bridge unit tests. The `Conversation.channel` / `chatwoot*` columns are dropped by migration `20261003140000_drop_chatwoot_bridge_columns`; `ChatMessage.origin` and `externalId` are kept as generic provenance/idempotency markers. The containers and volumes were removed.
