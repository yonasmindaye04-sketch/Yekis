# Changelog

All notable implementation and documentation changes are recorded here.

## Unreleased

### Removed
- **Chatwoot third-party agent inbox (2026-10-03)**: the Chatwoot integration built earlier the same day has been fully reverted. It was working (Application API client, signature-verified webhook, two-way message and status sync — all verified end to end against a live v4.18.0), but it was the wrong shape for this product:
  - It required a **public HTTPS tunnel** for webhooks. Chatwoot runs deliveries through `ssrf_filter`, which rejects every private/loopback address with no flag to relax it, so agent replies were silently undeliverable in local development and would have needed a public ingress in production.
  - It added a **second inbox, a second message store and a second UI** alongside the staff dashboard that already had a working support queue.
  - Its launcher bubble is **third-party and unstyleable**, which is precisely the "not embedded the way we want it" problem it was meant to solve.
  - It cost a ~3 GB container stack (its own Postgres and Redis) for capabilities the platform already had: realtime messaging, typing, read receipts, attachments, ticket assignment/claim/reassign, OPEN/CLOSED workflow, unread queues and audit trail.

  Everything the native path was missing turned out to be **scoped guest access** (see the Added entry above), not an agent inbox. Removed: the widget component and its SDK bridge, the Application API client, the bridge service, the webhook receiver, the signature helpers, `docker-compose.chatwoot.yml`, `.env.chatwoot.example`, the `chatwoot:*` npm scripts, all `CHATWOOT_*` env vars and both `.env` entries, and the bridge unit tests. The `Conversation.channel` / `chatwoot*` columns are dropped by migration `20261003140000_drop_chatwoot_bridge_columns`; `ChatMessage.origin` and `externalId` are kept as generic provenance/idempotency markers. The containers and volumes were removed.

### Added
- **Guest support can finally read and reply (2026-10-03)**: the landing support widget was a one-way dead end. `POST /api/v1/chat/guest` is public, but `GET/POST /api/v1/chat/conversations/:id/messages` sat behind `requireAuth` — so a visitor could create a ticket and then got `401` on every read and every follow-up. A staff reply was written to the database that the visitor never saw, which is exactly why the widget felt disconnected from the product.
  - `POST /api/v1/chat/guest` now returns an extra `accessToken`: a signed JWT with `typ: "guest_support"` and a single `conversationId`. No refresh token, no `role`/`staffRole` claims, 12h TTL — it is not a login token in any sense.
  - New `requireGuestChatAccess` middleware accepts it on the messages and read routes and pins it to that one conversation. Presenting it for a different `conversationId` returns `403 TOKEN_SCOPE_MISMATCH` instead of falling through to a weaker check, so a leaked guest token cannot be walked across threads.
  - The WebSocket handshake accepts guest tokens and forces `isStaff` off regardless of what the payload claims, so replies arrive live on the existing `chat:new_message` push.
  - `LandingSupportChat` rewritten: it stores the scoped token, opens its own `RealtimeSocketManager` instance (the app-wide singleton belongs to the logged-in session), re-reads the authoritative thread from the server so staff replies render on the correct side, and falls back to a 5s poll if the socket cannot connect.
  - `components/supportChatEvents.ts` lets the footer and any marketing surface open the one native widget instead of mounting a second copy.
  - `tests/guest-support-token.test.ts` — 6 cases: claim pinning, absence of role/staff claims, expiry, rejection of a forged signature, and correct classification of ordinary session tokens.

- **Chatwoot webhook payload shape — agent replies were silently dropped (2026-10-03)**: found only by running the integration against a live Chatwoot, not by unit tests. Chatwoot uses **two different payload shapes**, and the handler assumed one:
  - `message_created` / `message_updated`: the **message** is flattened to the top level (`{ event, id, content, message_type, private, conversation: {...} }`). There is no `message` sub-object — the handler read `envelope.message`, got `undefined`, and returned early. Every agent reply was discarded while the webhook still answered **HTTP 200**, so nothing looked broken.
  - `conversation_created` / `conversation_status_changed`: the **conversation** is flattened instead (`{ event, id, status, meta: { sender }, ... }`), so `envelope.conversation?.id` and `.status` were both undefined and status sync silently no-opped.
  
  Added `readMessage()` and `resolveConversation()` to normalize both shapes. `resolveConversation` is deliberately event-aware: for `message_*` events the top-level `id` is the *message* id, so falling back to it would look up bogus conversations — there is an explicit regression test for that. Contact identifiers are now read from `conversation.contact.identifier`, `conversation.meta.sender.identifier` or the flattened `meta.sender.identifier`. Suite grew to 25 tests in `tests/chatwoot-bridge.test.ts`, including both real payload shapes captured verbatim from a live instance.
- **Test suite was order-dependent and could not see `DATABASE_URL` (2026-10-03)**: several suites import `src/lib/prisma.js` directly, which constructs a `PrismaClient` without passing through `src/config/env.js`, so nothing ever ran `dotenv` and Prisma threw `Environment variable not found: DATABASE_URL`. These suites only passed by accident — vitest's thread pool reuses workers, so whichever suite imported `config/env` first left `process.env` populated for the next file in that worker. Adding or removing one test file reshuffled the distribution and broke them. Added `tests/setup-env.ts` and wired it via `setupFiles` in `vitest.config.ts`, so `.env` is loaded once for the whole run. **95/95 tests now pass across 11 files** (previously 57 across 10).
- **Chatwoot compose could never work as documented (2026-10-03)**: `docker compose` only auto-loads a file named `.env`, so the documented `.env.chatwoot` was silently ignored and every command aborted on the `:?` guards. Added root scripts `chatwoot:up` / `:down` / `:logs` / `:migrate` / `:ps` that pass `--env-file .env.chatwoot`, and documented why.
- **Pinned Chatwoot was ~2 years behind and cannot sign webhooks (2026-10-03)**: the stack was pinned to `v3.16.0`, whose `Webhooks::Trigger` sends only `content_type`/`accept` — no signature, no timestamp, and no `secret` column on `webhooks`. Outgoing webhook signing landed in Chatwoot PR #13573 (Feb 2026). Since the receiver rejects unsigned deliveries by design, the pinned version could never have worked. Bumped to `v4.18.0` (current stable), now parameterised via `CHATWOOT_VERSION`, with a comment explaining the minimum.
- **`prisma migrate deploy` failed on `20260829233000_gig_disputes_polymorphic` (2026-10-03)**: the migration aborted with `42701 column "gigOrderId" of relation "Dispute" already exists` on any database synchronised with `prisma db push` instead of `migrate`, blocking every subsequent migration. Rewrote it to be **idempotent** — `ADD COLUMN IF NOT EXISTS`, `CREATE INDEX IF NOT EXISTS`, and `DO $$ ... IF NOT EXISTS (pg_constraint) ... $$` guards around the FK and CHECK (Postgres has no `ADD CONSTRAINT IF NOT EXISTS`) — so it now converges a drifted database instead of failing, and is a safe no-op on a correctly migrated one. `migrate deploy` completes cleanly and `prisma migrate diff` reports no difference against `schema.prisma`.
  - This also closed a real integrity gap that the drift had been masking: **`schema.prisma` declares `Dispute.gigOrderId` as `@unique`, but no migration ever created that index.** Only `db push` had been supplying it, so a database built purely from migrations would have allowed several disputes against the same gig order — on the escrow/dispute money path. The migration now creates `Dispute_gigOrderId_key` explicitly.
  - `Dispute_subject_check` was also missing from the pushed schema, so "exactly one of `contractId` / `gigOrderId`" was documented in `schema.prisma` but never actually enforced. It is intentionally not guarded with a skip-if-violated clause: if rows violate it, the deploy must fail loudly rather than silently leave the money path unconstrained.
  - Verified all five behaviours directly against Postgres (in rolled-back transactions, no test data persisted): contract-only accepted, gig-only accepted, both-subjects rejected, neither-subject rejected, and a second dispute on the same gig order rejected by the unique index.
- **Chatwoot `db:chatwoot_prepare` was an easy-to-miss manual step (2026-10-03)**: the compose file required running `rails db:chatwoot_prepare` by hand before first boot, but the image entrypoint only waits for Postgres and does **not** migrate — so skipping it produced a stack that started and then failed cryptically against an empty schema. The task is idempotent by design (it loads the schema when `ar_internal_metadata` is absent, then always runs `db:migrate`), so it is now automated: a one-shot `chatwoot-migrate` service runs it, and both `chatwoot-web` and `chatwoot-worker` wait on it with `service_completed_successfully`. It also re-runs on every `up`, which is what makes Chatwoot image upgrades work without a manual step. `restart: "no"` avoids a crash loop; a failure blocks startup loudly instead.
  - Verified the gating pattern against a throwaway compose stack: the dependent starts only after a successful migration, is blocked (with a clear error) when the migration exits non-zero, and starts on the retry once the migration succeeds.
  - Collapsed the triplicated service definition into a `x-chatwoot-app` YAML anchor so web, worker and migrate cannot drift apart, and confirmed via `docker compose config` that all three receive the image, entrypoint, storage mount and full environment.
- **WebSocket IDOR — any user could subscribe to any conversation (2026-10-03)**: `lib/socket.ts` granted client-requested channel subscriptions with **no authorization check**, so any authenticated user could send `{ "action": "subscribe", "channel": "conversation:<any-id>" }` and receive another user's chat messages in real time. The `typing` and `read` actions had the same gap, leaking typing activity and read receipts across conversations.
