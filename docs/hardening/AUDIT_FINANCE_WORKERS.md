## CRITICAL

### C-1 ▸ downstream of "recordWalletTopUpLedger never called" — every disbursement journal violates a DB CHECK constraint, after the money has already left- **Severity:** CRITICAL
- **Confidence:** CONFIRMED (code path); magnitude depends on migration `20261009120000` being applied
- **Location:** `apps/backend/src/modules/escrow/escrow.service.ts:974-994`

**What's wrong:** The settlement asset accounts (`1000-ASSET-TELEBIRR`, `1010-ASSET-CBE`) are *only ever credited* by `recordWithdrawalDisbursementLedger`; their only debit — `recordWalletTopUpLedger` — is never called. The account therefore starts at 0 and every payout drives it negative, which the `LedgerAccount_balance_check` CHECK constraint rejects, aborting the journal transaction *after* the wallet was debited and the payout was already marked `CONFIRMED`.

**Evidence:**
```ts

  where: { userId: params.userId, balanceMinor: { gte: params.amountMinor } },
  data: { balanceMinor: { decrement: params.amountMinor } },
});
...
// escrow.service.ts:974-994if (disbursementResult.status === "CONFIRMED") {
  await prisma.payoutTransaction.update({
    where: { id: payout.id },
    data: { status: "CONFIRMED", providerPayoutId: ..., settledAt: new Date() },
  });                                    // ← committed
  await prisma.$transaction(async (tx) => {   // ← NOT wrapped in try/catch
    await recordWithdrawalDisbursementLedger(tx, { ... netAmountMinor ... });
  });
```
```ts
// ledger.service.ts:457-462  — the only entry that credits the asset
{ accountCode: assetAccount.code, ..., accountType: assetAccount.type,
  creditMinor: params.netAmountMinor },
```
```sql
-- migrations/20261009120000_ledger_and_payout_invariants/migration.sql:93-95
ALTER TABLE "LedgerAccount" ADD CONSTRAINT "LedgerAccount_balance_check"
  CHECK ("type" NOT IN ('ASSET', 'EXPENSE') OR "balanceMinor" >= 0);
```
Corroborating evidence that this is the live state: the same migration's header comment (`…/migration.sql:84-89`) records *"dev: 81 of 272 accounts are negative, all type=LIABILITY"* — exactly what you get when user-liability accounts are credited by releases/funding but never by top-ups.

**Failure mode:** user calls withdraw → wallet debited → payout `CONFIRMED` → journal throws `P2004` → route returns **500** (`escrow.routes.ts:287`) → user retries → **second** payout. The first disbursement already went out.

**Suggested fix:** Post a `WALLET_TOPUP` collection journal (Dr settlement asset / Cr user liability) from `handleTopUpWebhook`, `approveTopUp` and the provider-funded milestone path in `handlePaymentWebhook`, so the asset account has real inflow before any outflow.

### C-4 — `acceptGigOrder` accrues platform revenue **outside** the transaction and **unconditionally**, double-counting on a lost claim
- **Severity:** CRITICAL
- **Confidence:** CONFIRMED
- **Location:** `apps/backend/src/modules/gigs/gig.service.ts:604-623`

**What's wrong:** The transaction `return`s quietly when the release claim is lost, but `recordGigPlatformEarnings` runs unconditionally afterwards — so a losing concurrent accept (or any retry) still increments `PlatformOperatingAccount.accumulatedFeeMinor` / `accumulatedWithholdingMinor` and appends a `PlatformFeeCredit` row for a payout that never happened.

**Evidence:**
```ts
// gig.service.ts:604-623
await prisma.$transaction(async (tx) => {
  const claim = await tx.gigOrder.updateMany({
    where: { id: order.id, escrowState: "SUBMITTED_FOR_REVIEW" },
    data: { escrowState: "RELEASED", status: "COMPLETED", releasedAt: new Date() },
  });
  if (claim.count === 0) return;                       // ← silent no-op, tx commits
  await tx.wallet.update({ ... });
  await tx.user.update({ ... });
});

await recordGigPlatformEarnings(fees, order.id);       // ← OUTSIDE, UNCONDITIONAL
await gigAutoReleaseQueue.remove(`release-${order.id}`);
```
`recordGigPlatformEarnings` (`gig.service.ts:42-69`) increments the singleton account and inserts an append-only fee credit with no idempotency key at all.

**Suggested fix:** Move `recordGigPlatformEarnings` inside the transaction, throw `GigInvalidStateError` when `claim.count === 0`, and give `PlatformFeeCredit` a unique constraint on `(gigOrderId, createdAt-free)` — e.g. a `sourceKey` unique index — so replays cannot double-accrue.

### C-5 — Provider order is created *before* the local record; a uniqueness failure strands real money at Telebirr
- **Severity:** CRITICAL
- **Confidence:** CONFIRMED

### H-6 — Withholding is computed from mutable KYC state read at release, and is trivially avoidable by splitting a milestone

**Webhook / callback handlers**
- Telebirr signature is body-embedded RSA-PSS, verified against the raw body, and refuses to accept anything when `TELEBIRR_PUBLIC_KEY` is unset (`telebirr.client.ts:299-335`).
- Webhook routers are mounted **before** `express.json()` (`app.ts:56-67`), so the signature is verified over the exact provider bytes.
- The Telebirr SUCCESS path compares `callbackMinor` and currency against the *stored* order (`webhooks.routes.ts:135-155`) — it does not trust the callback amount.
- Provider mismatch is rejected (`escrow.service.ts:338-344`); already-settled callbacks are ignored (`:346-352`).
- `handleTopUpWebhook` refuses mock transaction ids in production (`topup.service.ts:347-375, 606`).
- `assertTopUpIsCreditable` is called on the manual-approval path too (`topup.service.ts:175`).

**Money typing**
- Every monetary column is Prisma `Int`: `PaymentTransaction.amountMinor/withholdingTaxMinor` (`schema.prisma:502,504`), `Wallet.balanceMinor` (`:517`), `WalletTopUp.amountMinor` (`:546`), `PayoutTransaction.*` (`:1337-1339`), `PlatformOperatingAccount.*` (`:989-993`), `PlatformFeeCredit.*` (`:1010-1013`), `LedgerEntry.debitMinor/creditMinor` (`:1313-1314`), `LedgerAccount.balanceMinor` (`:1283`). No `Float`, no `Decimal`, no JS `BigInt`.
- I exhaustively compared `Math.round(amount * rate)` against exact rational half-up rounding for rates `0.005 / 0.05 / 0.03 / 0.3` over `amount ∈ [1, 50000]` minor units: **zero divergences**. The `Math.round(gross * rate)` pattern (`fees.ts:27-41`) is safe for the configured rates. The remaining `/100`, `toFixed`, `toLocaleString` and `parseFloat` sites are display-only formatting (`bot/formatters/index.ts`, `serviceAgreement.template.ts:20`, `topup.service.ts:533,596,638`, `commands.ts:281`) or bot-scene stubs that never touch the DB (`bot/scenes/index.ts:121,183`).
- `webhooks.routes.ts:146` and `telebirr.client.ts:437` parse the provider's decimal string via `Math.round(Number(x) * 100)` — float parsing of money from an untrusted source. I verified this agrees with exact decimal parsing for all `\d+(\.\d{1,2})?` inputs in range, and the two implementations use the identical regex, so the webhook and the reconcile sweep cannot disagree. Style issue, not a demonstrated defect.

**Remittance / withholding format**
- No file is generated — `withholdingRemittance.worker.ts` writes a single aggregate row per period and a human files with ERA (documented at `:15-23` and `finance.service.ts:118-121`); `markWithholdingReportFiled` (`finance.service.ts:122-134`) only records the ERA reference. **No money moves to a bank account without a human step in this path.** The independent problems in this worker are M-13 and M-10.
