## CRITICAL

### C-1 — Arbitrary file read (LFI) on the API host via chat attachment key path traversal
- **Location:** `apps/backend/src/modules/chat/chat.routes.ts:247-254` (double-decode) → `apps/backend/src/lib/objectStore.ts:257` (traversal sink); gate satisfied via `apps/backend/src/modules/chat/chat.service.ts:409-428`; the key is attacker-authored at `apps/backend/src/modules/chat/chat.routes.ts:80` and stored verbatim at `apps/backend/src/modules/chat/chat.service.ts:513-515`.
- **What's wrong:** Any authenticated member can read arbitrary files readable by the Node process (including `.env` → `JWT_ACCESS_SECRET`, `DATABASE_URL`, `TELEBIRR_PRIVATE_KEY`), because `attachmentUrl` is an unvalidated client string that becomes the authorization token for `getChatAttachmentStream`, whose local-disk fallback joins the key onto `uploads/` without traversal normalisation.

**Evidence**

`chat.routes.ts:247-254` — Express already ran `decode_param` (one `decodeURIComponent`) on the path segment; the handler decodes a **second** time:
```ts

  const rawKey = req.params.key as string;
  key = decodeURIComponent(rawKey);
```
Verified with the installed router stack (express@4.22.2 / path-to-regexp@0.1.13): `/attachments/:key(*)` compiles to `^\/attachments(?:\/((.*)))\/?$`, and `lib/router/layer.js` assigns `req.params.key = decode_param(match[i])`.

`objectStore.ts:253-266`:
```ts
    try {
      const fs = await import("node:fs");
      const path = await import("node:path");
      const localFile = path.resolve(process.cwd(), "uploads", ...storageKey.split("/"));
      if (fs.existsSync(localFile)) {
        ...
        stream: fs.createReadStream(localFile),
```
`storageKey` is never checked for `..`; the S3 `GetObject` with a `..` key fails first and falls through to this branch.

`chat.routes.ts:78-82` — `attachmentUrl` is `z.string().optional()`, no `chat-attachments/` prefix or shape constraint:
```ts
const MessageInput = z.object({
  body: z.string().min(1).max(5000),
  attachmentUrl: z.string().optional(),
```

`chat.service.ts:409-419` — the "authorization" is only *"some message row somewhere has this exact URL"*:
```ts
  const url = `/api/v1/chat/attachments/${encodeURIComponent(params.storageKey)}`;
  const message = await prisma.chatMessage.findFirst({
    where: { attachmentUrl: url },
    select: { conversationId: true },
  });
  if (!message) return null;
```

**Exploit path**
1. `POST /api/v1/chat/conversations` (or `/support`) → get a conversation you are a participant of.
2. `POST /api/v1/chat/conversations/<id>/messages` with `{"body":"x","attachmentUrl":"/api/v1/chat/attachments/..%2F..%2F..%2F..%2F.env"}`.
3. `GET /api/v1/chat/attachments/..%2F..%2F..%2F..%2F.env` → `authorizeAttachmentAccess` matches your own message, `getChatAttachmentStream("../../../.env")` → `path.resolve(cwd,"uploads","..","..","..","..",".env")` → streamed back with the file bytes.

**Suggested fix:** Reject any key that is not an exact match of `^chat-attachments\/[0-9a-f]{2}\/[0-9a-f-]{36}-[A-Za-z0-9._-]+$` before both the authorization lookup and the stream; in `getChatAttachmentStream` resolve with `path.basename(key)` under the fixed shard dir, or drop the local-disk fallback entirely. Also stop double-decoding (use `req.params.key` as-is).

## HIGH

### H-1 — `withdrawProposal` / non-accepted `decideProposal` write proposal status unconditionally, racing an acceptance
- **Location:** `apps/backend/src/modules/jobs/proposals.service.ts:240-243` (withdraw) and `:132-136` (shortlist/reject), versus the guarded accept at `:171-180`.
- **What's wrong:** Both paths read the status, then write it with an unguarded `prisma.proposal.update`, so a freelancer withdrawing (or a client rejecting) at the same moment the other party accepts overwrites `ACCEPTED` with `WITHDRAWN`/`REJECTED` — after the accept transaction already flipped the job to `IN_PROGRESS` and (for accept) created the Contract.

**Evidence**
```ts
// proposals.service.ts:227-243
  const proposal = await prisma.proposal.findUnique({ where: { id: params.proposalId } });
  if (!proposal) throw new ProposalNotFoundError();
  if (proposal.freelancerId !== params.requestingUserId) throw new ForbiddenRoleError("Not your proposal.");
  if (proposal.status !== "SUBMITTED" && proposal.status !== "SHORTLISTED") { ... }
  const updated = await prisma.proposal.update({
    where: { id: proposal.id },
    data: { status: "WITHDRAWN" },
  });
```
Contrast the accept branch, which *is* guarded:
```ts
// proposals.service.ts:171-180
      const accepted = await tx.proposal.updateMany({
        where: { id: proposal.id, status: { in: ["SUBMITTED", "SHORTLISTED"] } },
        data: { status: "ACCEPTED" },
      });
      if (accepted.count !== 1) throw new InvalidJobStateError("Proposal can no longer be accepted.");
```
A concurrent `REJECTED` landing between the read at `:128` and the write at `:133` also makes `createContractFromProposal` (`:218`) throw `ProposalNotAcceptedError` → HTTP 500 with the proposal already `ACCEPTED`.

**Suggested fix:** Replace both writes with `updateMany({ where: { id, status: { in: [...] } } })` and throw `InvalidJobStateError` when `count !== 1`, exactly as the accept branch does.

### H-5 — WebSocket authentication skips the suspension / `session_version` checks that `requireAuth` performs
- **Location:** `apps/backend/src/lib/socket.ts:59-89` vs `apps/backend/src/middleware/auth.ts:157-189`.

**Evidence**

**Suggested fix:** Factor the post-verify checks in `auth.ts:157-189` into a shared helper and call it from the `wss.on("connection")` handler before registering the socket; additionally re-check on the heartbeat tick.

### M-4 — Chat attachments are served with the uploader-controlled `Content-Type` (stored HTML/XSS on the API origin)
- **Location:** `apps/backend/src/modules/chat/chat.routes.ts:226-239` (upload) and `:269-284` (serve); `apps/backend/src/lib/objectStore.ts:206-214, 249`.
