### H-5. Float→minor-unit conversion produces non-integers that the backend rejects (`POST /api/v1/jobs`)
- **Frontend:** `apps/frontend/src/App.tsx:720`, `:724`, `:731`
- **Backend/Schema:** `packages/schemas/src/index.ts:86-89`, route at `apps/backend/src/modules/jobs/jobs.routes.ts:79`
- **What's wrong:** `Number(x) * 100` is not always an integer in IEEE-754, and `Money.amountMinor` requires `.int()`, so posting a job whose budget has two decimals commonly fails validation.

**Evidence (frontend):**

```ts
  amount: { amountMinor: Number(jobForm.budgetMax) * 100, currency: "ETB" }, ... }],
```
**Evidence (backend schema):**
```ts
// packages/schemas/src/index.ts:86-89
export const Money = z.object({
  amountMinor: z.number().int().nonnegative(), // e.g. 150000 = 1,500.00 ETB
  currency: z.literal("ETB"),
});
```
Verified failure cases (Node): `0.29→28.999999999999996`, `1.15→114.99999999999999`, `8.29→828.9999999999999`, `4.35→434.99999999999994`, `19.99→1998.9999999999998`, `2.675→267.5`.

### H-7. WebSocket auth skips the suspension and session-revocation checks that `requireAuth` performs
- **Backend (WS):** `apps/backend/src/lib/socket.ts:41-89`
- **Backend (HTTP, for contrast):** `apps/backend/src/middleware/auth.ts:157-189`
- **Frontend caller:** `apps/frontend/src/api/socket.ts:49`
- **What's wrong:** The WS handshake verifies the JWT signature and nothing else, then derives `isStaff` from the token's `staffRole` claim. It never re-reads the user row, so a staff member whose role was just revoked — or any suspended user — keeps a live socket with `staff:alerts` and `user:<id>` subscriptions until it disconnects. *(Same defect as open-critical #3 in the hardening brief.)*

**Evidence (WS handler, no DB read at all):**
```ts
// socket.ts:59-89
const { payload } = await jwtVerify(token, secretKey);
const staffRole = payload.staffRole as string | undefined;
ws.isStaff = isGuestToken ? false : !!staffRole;
subscribeToChannel(ws, `user:${userId}`);
if (ws.isStaff) subscribeToChannel(ws, "staff:alerts");
```
**Evidence (HTTP path does check):**
```ts
// auth.ts:157-189
const user = await prisma.user.findUnique({ where: { id },
  select: { isSuspended: true, isGuestContact: true } });
if (user.isSuspended) return res.status(403).json({ error: "ACCOUNT_SUSPENDED" });
const tokenVersion = (payload as Record<string, unknown>).session_version;
if (tokenVersion !== (rows[0]?.sessionVersion ?? 0))
  return res.status(401).json({ error: "SESSION_REVOKED" });
```
**The revocation is deliberate but WS-blind** — both staff-mutation routes bump `sessionVersion` specifically to revoke live sessions:
```ts
// admin.routes.ts:566 (role change)
await prisma.$executeRaw`UPDATE "User" SET "sessionVersion" = "sessionVersion" + 1 WHERE id = ${targetUserId}`;
// admin.routes.ts:658 (suspension), inside the same Serializable transaction
await tx.$executeRaw`UPDATE "User" SET "sessionVersion" = "sessionVersion" + 1 WHERE id = ${targetUserId}`;
```

**Fix:** Reuse `requireAuth`'s checks in the `connection` handler — load `isSuspended`/`sessionVersion` and `ws.close(4003, …)` on mismatch. The 30s heartbeat at `socket.ts:170-181` gives a natural place to re-validate periodically.

### M-4. Both tokens are persisted in `localStorage`, where any XSS becomes full session theft
