### H1 — A second, weaker copy of the gig-moderation action lets COMPLIANCE/OPERATIONS publish gigs without the permission or step-up
- **Area:** B (root cause is the A-side permission matrix)
- **Location:** `apps/backend/src/modules/gigs/gig.routes.ts:207-216` vs `apps/backend/src/modules/admin/admin.routes.ts:114-117`
- **What's wrong:** The same privileged action (publishing a gig → ACTIVE) is exposed twice; the public copy is guarded by a role list that grants the power to roles the canonical matrix deliberately denies it, and omits `requireFreshAuth` entirely.

**Evidence**
```ts
// gig.routes.ts:207-216  — POST /api/v1/gigs/:gigId/moderation
gigsRouter.post(
  "/:gigId/moderation",
  requireAuth,
  requireStaffRole(
    "COMPLIANCE_OFFICER",
    "COMPLIANCE_ADMIN",
    "ADMIN",
    "OPERATIONS_ADMIN",
    "SUPER_ADMIN",
  ),
```
```ts
// admin.routes.ts:114-117 — POST /api/v1/admin/gigs/:gigId/moderation
adminRouter.post(
  "/gigs/:gigId/moderation",
  requireFreshAuth(300),
  requirePermission("gigs.moderate"),
```
```ts
// permissions.ts:19 (declared) — granted ONLY by ALL (SUPER_ADMIN/ADMIN).
// OPERATIONS_ADMIN (89-102) and COMPLIANCE_SET (67-82) do not contain "gigs.moderate".
```
So `COMPLIANCE_OFFICER`, `COMPLIANCE_ADMIN` and `OPERATIONS_ADMIN` are **refused** at `/admin/gigs/:id/moderation` but **succeed** at `/gigs/:id/moderation` — the weaker guard is the one that works. Both call `moderateGigStatus` (`gig.service.ts:199`), which additionally never checks that the moderator is not the gig owner (`gig.service.ts:205-211` only does `findUnique` → `update`).

**Suggested fix:** Delete `gig.routes.ts:207-246` and keep only the `/admin` route; if both must exist, apply `requireFreshAuth(300) + requirePermission("gigs.moderate")` to both.

### H2 — Gig dispute settlement is not atomic: the escrow claim commits before the wallet credit
- **Area:** B
- **Location:** `apps/backend/src/modules/gigs/gigDispute.service.ts:207-224`, `:226-239`, `:245-274`
- **What's wrong:** Each resolution branch commits the `escrowState` claim in its own auto-commit statement and *then* credits the wallet, so a failure between the two leaves a RELEASED/REFUNDED/PARTIAL_REFUND order that paid nobody — the exact F-04 failure the milestone path was rewritten to prevent.

**Evidence**
```ts
// gigDispute.service.ts:207-224
    const claim = await prisma.gigOrder.updateMany({
      where: { id: order.id, escrowState: "DISPUTED" },
      data: { escrowState: "RELEASED", status: "COMPLETED", releasedAt: new Date() },
    });
    if (claim.count === 0) { throw new InvalidGigDisputeStateError(...); }

    await prisma.wallet.update({                       // ← NOT in the same transaction
      where: { userId: order.gig.freelancerId },
      data: { balanceMinor: { increment: fees.freelancerNetMinor } },
    });
```
`prisma.wallet.update` throws `P2025` if the freelancer has no `Wallet` row, and any throw here is caught by `gig.routes.ts:521-530` and turned into a 500 **after** the order is already marked `COMPLETED`. Contrast the milestone path, which does the claim + all credits in one transaction and passes `tx` down:
```ts
// dispute.service.ts:488-535
  await prisma.$transaction(async (tx) => {
    const claim = await tx.dispute.updateMany({ ... });
    ...
    await releaseMilestoneFunds(milestone.id, contract.freelancerId, milestone.amountMinor, { tx });
```
Note `acceptGigOrder` (`gig.service.ts:604-619`) *does* wrap its claim+credit — the dispute path is the inconsistent one.

**Suggested fix:** Wrap each `resolveGigDispute` branch in `prisma.$transaction` (or route the credits through helpers that accept `tx`), and set the `Dispute.stage` update inside it.

### H4 — Parties can settle and pay out their own dispute at Stage 1, with no staff involvement and `resolvedByStaffId` forged
- **Area:** C
- **Location:** `disputes/dispute.routes.ts:300-302` → `dispute.service.ts:892-904` → `dispute.service.ts:494-507`
- **What's wrong:** `POST /:disputeId/withdraw` is guarded by `requireAuth` only; when the second party confirms, it calls the staff money-moving `resolveDispute` passing the **party's own user id** as `staffUserId`, so escrow is released/refunded with zero evidence, zero staff review, zero step-up — and the resolution is persisted as if a staff member made it.

**Evidence**
```ts
// dispute.routes.ts:300-303
disputesRouter.post(
  "/:disputeId/withdraw",
  requireAuth,
```
```ts
// dispute.service.ts:834-840  (first caller only records a proposal)
  if (!dispute.withdrawalRequestedByUserId) { ... withdrawalRequestedByUserId: params.userId ... }

// dispute.service.ts:892-904  (second caller pays out)
  await prisma.dispute.update({
    where: { id: dispute.id },
    data: { stage: "STAGE_3_MEDIATION", withdrawalConfirmedAt: new Date() },
  });

  const resolved = await resolveDispute({
    staffUserId: params.userId,           // ← a CLIENT/FREELANCER id
    disputeId: params.disputeId,
    outcome: params.proposedOutcome,
```
`Dispute.resolvedByStaffId` is an unconstrained nullable string (`prisma/schema.prisma:587`) so nothing rejects it, and `resolveDispute` accepts the claim from `STAGE_1_NEGOTIATION` because the handler has just promoted the stage. `refundMilestoneToClient` happily refunds from `ESCROW_HELD`/`WORK_IN_PROGRESS` (`escrow.service.ts:1051-1059`). No `requireFreshAuth`, so a Telegram/OAuth-only session (`amr` weak) can do it too.

**Suggested fix:** Route mutual settlement through a separate service function that (a) requires `requireFreshAuth`, (b) passes `staffUserId: null` with a distinct `resolutionSource`, and (c) records a `DISPUTE_MUTUAL_WITHDRAWAL_CONFIRMED` actor rather than writing the party id into `resolvedByStaffId`.
